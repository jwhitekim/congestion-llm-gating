## 1. 하네스 컴포넌트 감사 (레포 코드 대조)

기존 코드를 표준 Agent Harness 9개 컴포넌트에 대조한 결과:

| 컴포넌트 | 상태 | 근거 |
|---|---|---|
| System Prompt | ✅ 완전 구현 | `agent/prompt.py` |
| Orchestrator | ✅ 완전 구현, 2계층 | `main.py`(파이프라인) + `agent/loop.py`(LLM 루프) |
| Tool Registry | ✅ 완전 구현 | `agent/tools/__init__.py`, `@register_tool` 데코레이터 |
| Validation | ✅ 완전 구현 | `agent/schema.py`, 금지 필드 제거 로직 포함 |
| State/Memory | ⚠️ 부분(LLM엔 없음, 시스템엔 있음) | `SegmentHistory`(ring buffer)는 시스템 레벨에만 존재 |
| Retry/Timeout | ⚠️ timeout만 있음, retry 없음 | `timeout=30.0`뿐, 실패 시 파이프라인 전체가 죽음(버그) |
| Logging/Tracing | ⚠️ 로깅만, 트레이싱 아님 | CV/agent 시간 미분리 |
| Evaluation | ❌ 없음 | 그라운드 트루 없음 |
| Runtime Environment | ✅ 구현, 단, 동기 블로킹 | 비동기 아님 |

**결론:** 4개 완전, 3개 부분, 1개 부재. → "완전한 표준 하네스"가 아니라 **"트리거 게이팅된 경량 하네스"**라는 게 논문 프레이밍.

## 4. 발견 1 — rule-based level은 이미 절반 구현돼 있었음

- `trigger/rules.py`의 `_classify_level()`이 이미 **매 세그먼트마다** density 기반으로 level을 계산 (트리거 여부 무관)
- `io_utils/session.py`도 이미 **매 세그먼트마다** `results.jsonl`에 level을 기록
- **진짜 남은 문제:** `io_utils/reporter.py`(터미널 출력)만 트리거 없으면 level을 안 보여줌 — 표시(display) 문제일 뿐, 데이터 문제 아님
- 원래 "치명적 결함"이라고 분류했던 것보다 작업량이 훨씬 작음

## 5. 발견 2 — track_people 도구가 순환적(redundant)

- `agent/loop.py`의 `_facts_to_text()`가 초기 프롬프트에 이미 넣는 것: 총 인원, 밀도, 평균 속도, 구역별 인원, 밀도 변화율, 속도 추세, 혼잡 수준
- `track_people` 도구가 반환하는 것: **완전히 동일한 필드셋**
- → LLM이 도구를 호출해도 새 정보가 전혀 없음. "도구가 있는 척"만 하는 상태

### 부가 발견: zone 파라미터 버그
```python
if metric in ("density", "all"):
    result["facts"]["density"] = round(current.density, 2)   # zone 파라미터 무시, 항상 전역값 반환
```
- `count`만 zone별로 실제 필터링됨(이미 프롬프트에 있어서 무의미)
- `density`/`speed`는 zone 인자를 무시하고 전역값을 그대로 반환 — "구역별 계산"이 애초에 구현된 적 없음

## 7. 거부된 방향 — 영상→텍스트 인코딩

- "영상을 텍스트로 인코딩/추출해서 에이전트에 입력"하는 아이디어가 나왔으나 **기각**
- 이유: LLMAgentSystem(VLM 기반)에서 이미 실패했던 패턴의 변형. 영상을 "서술형 텍스트"로 바꾸는 주체가 이미 암묵적 판단을 수행하게 되어, "지각은 코드, 판단은 LLM"이라는 핵심 경계가 다시 무너짐
- 구조 전체를 뒤엎을 필요 없음 — 지금 구조(CV=숫자 사실, LLM=텍스트 기반 판단) 유지

## 8. 에이전트 역할 재정의 — "판단자"가 아니라 "해석자/조정자"

### 발견 (사용자 본인 통찰)
카페에서 직접 audit한 결과: 스키마 필드 6개 중 거의 전부가 규칙으로 대체 가능함을 발견.

| 필드 | 규칙 대체 가능 여부 |
|---|---|
| congestion_level | ✅ 이미 rule-based로 이동 결정 |
| local_hotspots | ✅ 규칙 가능 (`zone_counts[z] > ZONE_MAX` 조건 이미 존재) |
| 전체혼잡 vs 국소혼잡 | ⚠️ 규칙 가능 (구역별 편차/분산 계산) |
| 스파이크 vs 지속변화 | ⚠️ 규칙 가능 (지속시간 카운터) |
| action | ⚠️ 규칙 가능 (level+지속성 조합 결정 테이블) |

### ChatGPT 교차검증 1차 결과 (일치)
- 판단 기준 대부분이 수치 규칙으로 대체 가능하다는 점 확인
- **추가 지적:** 판단에 필수적인 정보(zone 정규화 밀도, 지속시간/초과비율, 밀도 추세, 시간대 기준선)를 **도구 호출 뒤에 숨기는 것은 "인위적으로 에이전트성을 만드는 설계"**라는 비판 — 애초에 세션 히스토리 조회 도구안이 이 지적에 걸려 철회됨
- **시간대 맥락**: 프롬프트에 "고려하라"고 써있지만 실제 입력엔 관련 데이터가 전혀 없음 → 프롬프트에서 해당 문장 삭제 (기준선 데이터 구축은 5일 스코프 밖)
- **원칙 충돌 지적:** LLM에게 rule-based congestion_level을 입력으로 주면서 LLM도 별도로 congestion_level을 판단하게 하면 판단이 중복됨 → **선택 B(규칙이 판정, LLM은 해석)로 확정**

### 최종 agent 역할
> **"규칙끼리 신호가 상충하는 경계 사례를 해석·조정하고, 사람이 읽을 수 있는 서술로 종합한다"**

- 예: 밀도는 상승하는데 속도도 상승(모순 신호), 전역은 medium인데 특정 구역만 장시간 초과(전역-국소 불일치)
- 이게 LLM이 실제로 호출되는 새로운 트리거 사유("conflict" 트리거)가 됨

### 검토했다 폐기된 후보들

## 10. 구역별 밀도 모듈 — 삭제 논쟁과 최종 결론

### 논쟁의 발단
"기존 전역 밀도 + 트리거 조건만으로 국소 혼잡 문제가 저절로 해결되지 않을까?"라는 제안이 나옴.

### 왜 이게 중요한가 — 원래 연구 동기 재확인
과거 세션(LLMAgentSystem 기획 당시) 기록 확인 결과, **"기존 density 기반 시스템이 국소적 뭉침을 전역 혼잡으로 오판한다"**는 것이 이 프로젝트 전체의 **실측된, grounded 연구 동기**였음이 확인됨. 즉 구역별 밀도 처리는 새로 추가하는 기능이 아니라 **원래 문제의 핵심**.

### ChatGPT 교차검증 2차 결과 (수식 반례로 확정)
- 소수 인원(k) 밀집 시 전역 density에 대한 가중치는 $k(k-1)/N(N-1)$ 수준 — 예: 30명 중 5명 밀집 시 약 2.3%만 반영, 사실상 희석됨
- **결정적 반례:** 5㎡ 구역에 7명이 완전 정지 상태로 밀집, 나머지 20명은 넓은 구역에서 정상 이동 중인 상황
  - hotspot: 7 ≤ 8 → 미발동
  - stagnation: 전역 평균속도가 이동 중인 20명에 끌려 올라가 → 미발동
  - surge: 밀집 인원 쌍 비중 5.98%뿐이라 density 증가율 2.2%(기준 40%) → 미발동
  - **결과: 트리거 3개 다 안 걸리고 LLM도 안 불림. 실제로는 심각한 국소 혼잡 상황(명확한 미탐 반례)**
- hotspot 트리거(인원수 임계값)는 zone 면적 차이를 무시해 **역전 현상**도 만듦(넓은 구역의 느슨한 9명은 걸리고, 좁은 구역의 촘촘한 7명은 안 걸림)

### 최종 결론
**구역별 밀도 처리 모듈은 삭제 불가.** 다만:
- **1순위(면적/수용량 정규화, $n_z/A_z$)가 이상적**이나, zone별 실제 면적 데이터가 없어 5일 스코프 밖
- **2순위(zone-scoped Line Density 재적용)로 현실적 구현** — 어제 결정한 방향 그대로 유지
- **논문에 정직하게 한계 명시**: "이는 물리적 밀도의 근사치이며 완전한 면적 정규화 밀도가 아니다"
- 구현 시 주의: zone 내 인원수 n<2일 때 pairwise distance 불안정 → 별도 처리 필요

## 11. 최종 확정 아키텍처

### 파이프라인 (perception, 항상 실행)
- 객체탐지(YOLO) → 추적(OC-SORT) → **전역 밀도 계산** (기존 유지)
- **[신규]** zone별 정규화 밀도 (zone-scoped `calc_spatial_density` 재적용, n<2 처리 포함)
- **[신규]** zone 집중도 지표 (max/mean 비율, 변동계수)
- **[신규]** 지속시간/초과비율 카운터 (전역 + 구역별)
- **[신규]** 밀도 추세(slope) — 기존엔 `speed_trend`만 있었음, `density_slope` 추가
- **rule-based level 상시 계산** (이미 구현돼 있었음 — `reporter.py`만 수정하면 노출됨)

### 트리거 (rule 기반, 항상 실행)
- 기존 3개 유지: surge, stagnation, hotspot
- **[신규]** conflict 트리거 — 신호 상충 감지 (예: 밀도↑ + 속도↑ 모순, 전역-국소 불일치)

### 에이전트 (트리거 시에만 소환)
- 역할: "판단자"가 아니라 **"규칙이 명확히 못 가르는 경계/상충 사례의 해석자 + 서술자"**
- 스키마에서 `congestion_level` 제거 (코드가 rule-based level 주입)
- 프롬프트에서 "시간대 맥락 고려" 문장 삭제
- `local_hotspots`/`action` 필드도 규칙화 여지 있음 — **완전 제거 여부는 미확정** (다음 세션에서 결정)

### 도구
- `track_people` 삭제
- 모든 정보 격차는 파이프라인 상시 상태로 흡수, 도구 0개
- registry 패턴 코드는 유지 (확장성 설계 근거만 논문에 서술)

### 액션
- `alert`/`monitor`/`none` 레이블만 유지, 실행 dispatcher는 미구현, future work로 명시
